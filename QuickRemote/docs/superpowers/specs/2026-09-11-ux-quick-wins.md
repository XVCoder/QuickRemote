## 1. 背景与目标

当前版本的远程操控能力已经相当完整（悬浮球三键圆盘、空白区触摸板、Win11 手势全集、
双指缩放/滚动手感、参数化画质下发、访问验证码）。**剩下的体验缺口集中在"连接之前"和
"用完之后想调一下"这两端**，而不是操控本身。

本轮只做 5 件低成本高感知的事，不动协议主干、不改编码链路：

| 编号 | 功能 | 类型 |
|---|---|---|
| F1 | 音频死开关下线 | 缺陷修复 |
| F2 | 扫码 / 配置串配对 | 新增 |
| F3 | 会话内画质快捷面板 | 新增 |
| F4 | 剪贴板双向同步（纯文本） | 新增 |
| F5 | 断线自动重连 | 新增 |

**明确不在本轮范围**：音频重定向真实实现、文件传输、多显示器切换、自适应码率、
隐私屏、连接审批白名单、WOL。（已记入后续排期池，本次不做。）

## 2. F1 音频死开关下线

### 问题

`audioRedirect` 是一条贯通三层、却没有任何一层的消费端：

- `SettingsStore.kt:37` 定义 `AUDIO_REDIRECT` 键，`:67` 读取、`:115` 写入
- `Models.kt:111` 定义 `AppSettings.audioRedirect` 字段
- `SettingsScreen.kt:369-374` 渲染「音频」分区开关
- **PC 端全量搜索 `audio` / `wasapi`：零命中**，没有音频采集、没有编码、没有传输

用户打开它不会有任何事发生，属于对用户撒谎。

### 方案

删除 Android 端「音频」分区与 `audioRedirect` 全链路字段。不保留"即将推出"占位——
空占位同样是误导。

### 改动点

| 文件 | 改动 |
|---|---|
| `SettingsScreen.kt` | 删除 `SectionTitle("音频")` 及其开关（:369-379） |
| `SettingsStore.kt` | 删除 `AUDIO_REDIRECT` 键定义（:37）、读取（:67）、写入（:115） |
| `Models.kt` | 删除 `AppSettings.audioRedirect` 与其默认 `copy` 调用（:111） |

### 验收

- Android 设置页不再出现「音频」分区
- 已装用户升级后不崩溃（残留的旧 DataStore 键被忽略即可，无需清理）

## 3. F2 扫码 / 配置串配对

### 问题

新用户第一次连接要手工完成：记下 PC 服务器地址 → 抄到手机 → 再抄一遍 32 位预共享密钥。
这是整个产品最高、也最没必要的一道坎。

### 方案：**不新增任何 Android 依赖**

二维码由 **PC 端**生成，手机用**系统相机**扫。二维码内容是自定义 scheme 深链，
Android App 注册 intent-filter 接收即可：

```
quickremote://pair?d=<base64url(UTF-8 JSON)>
```

JSON 载荷：

```json
{ "v": 1, "addr": "relay.example.com:8444", "psk": "……", "name": "书房主机" }
```

**为什么用深链而不是 App 内置扫码器**：内置扫码需要引入 CameraX + ML Kit barcode
（或 ZXing）、申请相机权限、处理预览生命周期，并显著增大 APK。而深链方案
Android 端**零新增依赖**，只加几行 intent-filter 与一段解析逻辑。

**兜底路径**（应对部分 ROM 相机不识别自定义 scheme）：PC 配对窗口同时展示
**明文配置串**（同一 JSON 的 base64），Android 设置页「服务器」区新增
**「粘贴配置导入」**入口，用户复制粘贴即可。

### 交互

**PC 端** — 设置中心 →「基本配置」卡片新增按钮「手机配对」：
1. 点击弹出配对窗口（沿用现有 `DialogWindow` 深色圆角风格）
2. 顶部：二维码（约 240×240，深色底 + 浅色码以适应全局暗色主题）
3. 中部：明文配置串（可滚动单行 + 「复制」按钮）
4. 底部说明：「用手机相机扫描二维码，或复制配置串后在 App 设置页导入」

**Android 端**：
1. `MainActivity` 解析 `quickremote://pair` → 解码校验 → 写入 `SettingsStore`
   （`serverAddress` + `preSharedKey`）
2. 弹出结果提示：「已导入配置：书房主机」，随后自动刷新设备列表
3. 校验失败（版本号不支持 / 字段缺失 / base64 损坏）→ 明确提示，不静默失败
4. 冷启动与热启动（`launchMode` 保持 standard，用 `onCreate` + `onNewIntent` 双入口解析）

### 安全说明

预共享密钥以明文（仅 base64 编码）印在二维码上。这**不引入新的暴露面**——
密钥本来就要由用户手工抄写，二维码只是换了载体。但需在配对窗口加一行提示：
「请勿截图分享此二维码，它等同于你的密钥」。
若 PC 端配置的 PSK 仍为默认值 `change-me-please`，配对窗口顶部显示醒目警告并
引导先修改（`AppConfig.cs:110` 的默认值）。

### 依赖变更

| 端 | 变更 |
|---|---|
| PC | 新增 `QRCoder`（纯托管、无原生依赖、体积极小，用于生成二维码位图） |
| Android | **无新增依赖**；仅 `AndroidManifest.xml` 增加一个 intent-filter |

### 验收

- 系统相机扫二维码 → 直接拉起 QuickRemote 并完成配置写入
- 复制配置串 → App 设置页「粘贴配置导入」→ 同样成功
- 配置写入后设备列表能拉到 PC
- PSK 为默认值时显示警告
- 扫码后 App 内服务器地址/预共享密钥与 PC 端完全一致

## 4. F3 会话内画质快捷面板

### 问题

`qualityPercent` 只在 `SessionViewModel.kt:171` 初始化会话时读取一次。
连上之后想调画质，必须**断开 → 回设置页 → 改滑块 → 重新连接**。
而"网络突然变差"恰恰是最需要立刻降画质的场景。

### 方案：复用已有控制帧，**服务端零改动**

PC 端 `RemoteSessionManager.cs:1471` 已能处理 `{"action":"quality","percent":N}`，
Android 端 `RemoteSessionManager.kt:262` 已有 `sendQualityControl()`。
本轮只是把这条已有通路**接一个 UI 入口**。

**入口**：远程会话底部工具栏新增第 5 个按钮「画质」，
点击在画面上方弹出横向浮层（不遮挡画面中心）：

```
画质  [ 流畅 ][ 标准 ][ 高清 ][ 原画 ]
        40%    60%     80%    100%
```

- 4 档预设，点击立即生效（复用 `sendQualityControl`）
- 当前档位高亮；档位与 `qualityPercent` 的映射：
  流畅=40 / 标准=60 / 高清=80 / 原画=100
- 面板选择**只作用于当次会话**，同时写回 `SettingsStore.qualityPercent` 作为下次默认
- 工具栏按钮数由 4 → 5，需重新分配 `SpaceEvenly` 权重，图标用 `Icons.Filled.Tune`

### 改动点

| 文件 | 改动 |
|---|---|
| `RemoteSessionScreen.kt` | 底部工具栏加「画质」按钮 + 浮层组件 |
| `SessionViewModel.kt` | 暴露 `setQuality(percent)`，调用 `RemoteSessionManager.sendQualityControl` |
| `RemoteSessionManager.kt` | `sendQualityControl` 由 `private` 改为可被 ViewModel 调用（或加公开包装），`qualityPercent` 改为可写 |

### 验收

- 会话中切到「流畅」，PC 端日志出现 `Quality adjust request: 40%`，码率下降可观测
- 画质切换不中断画面、不重连、不黑屏
- 断开重连后按上次选择生效

## 5. F4 剪贴板双向同步（纯文本）

### 问题

远程办公最高频刚需，目前**完全为零**——`clipboard` 相关代码只用于复制日志和密钥。

### 协议

复用 `TYPE_CONTROL (0x05)`，载荷为 JSON，与已有 `quality` / `configure` / `keyframe`
同一分发器（PC 端 `HandleControlFrame`、Android 端控制帧接收分支）：

```json
{ "action": "clipboard", "seq": 3, "total": 1, "text": "……" }
```

- 单帧承载上限 **64KB（UTF-8 字节）**，超出按 `seq/total` 分片，
  接收端集齐后拼接再应用；单片超时 5 秒丢弃整组
- 超长文本（> 256KB）直接放弃同步并记日志，不做截断（半截内容比不同步更危险）

### 防回环

两端各自保存 `lastAppliedText`（做 SHA-256 取前 16 字节比对，避免整串驻留）：
**收到内容与 `lastAppliedText` 相同则直接丢弃，不写入系统剪贴板**。
这样"PC 复制 → 推到手机 → 手机剪贴板变化被本地监听 → 再推回 PC"的环会被切断。

### 触发时机

**PC → Android（主控端复制）**
- PC 端注册 `AddClipboardFormatListener`（消息窗口），剪贴板变化即推送
- Android 端收到后写入系统剪贴板。Android 10+ 前台应用写剪贴板合法，
  会话中 App 恒为前台，无兼容问题

**Android → PC（主控端复制）**
- Android 端在 App 从后台回到前台、以及会话内任意工具面板操作后检查一次剪贴板
  （Android 10+ 禁止后台读取剪贴板，**不能做轮询**），变化则推送
- PC 端收到后写入系统剪贴板

### 限制说明（写入设置页与更新记录）

- 仅纯文本，不含图片/文件
- Android 端受系统限制，只能在 App 处于前台时读取手机侧剪贴板；
  **PC 侧剪贴板始终实时同步到手机**（这是主要使用方向）

### 改动点

| 文件 | 改动 |
|---|---|
| `RemoteFrameProtocol.kt` / `RemoteFrameProtocol.cs` | 无需改（复用 TYPE_CONTROL） |
| `RemoteSessionManager.kt` | 发送 `clipboard` 控制帧；接收分支处理分片重组与写入 |
| `RemoteSessionManager.cs` | `HandleControlFrame` 加 `clipboard` 分支；新增剪贴板监听与推送 |
| `ClipboardSync.cs`（新，PC） | 剪贴板监听、去重、分片、Win32 读写封装 |
| `SessionViewModel.kt` | 会话内触发一次 Android 侧剪贴板检查 |

### 验收

- PC 复制一段中文 → 手机在会话中粘贴出完全一致的内容
- 手机复制一段文字 → 切回 App → PC 剪贴板更新（可粘贴验证）
- 复制 10 万字符文本 → 分片正常重组，或按规则明确放弃并记日志
- **无回环**：同一段文本不会在两端反复来回推送（日志中每个 seq 组只出现一次）
- 断网期间的剪贴板变化不阻塞会话、不崩溃

## 6. F5 断线自动重连

### 问题

Android 端目前只有 30 秒无数据看门狗**主动断开**（`RemoteSessionManager.kt:250-257`），
断开后停在错误浮层，用户必须手点「重新连接」（`RemoteSessionScreen.kt:1666-1674`）。
地铁、电梯、切 Wi-Fi/4G 这些瞬断场景下，用户体感就是"又掉了"。

### 方案：指数退避自动重连 + 最后画面保留

**退避序列**：`1s → 2s → 4s → 8s → 15s → 15s…`，最多 **8 次**（约 75 秒），
之后停下并显示原错误浮层 + 手动「重新连接」。

**重连期间 UI**（替换现有黑屏）：
1. **保留最后一帧画面并叠加半透明遮罩**（不是黑屏）——用户知道连接有救
2. 遮罩中央显示 `第 3/8 次重连 · 4 秒后重试`，并在浮层上提供
   **「立即重试」** 与 **「取消」** 两个按钮，不剥夺用户控制权
3. 重连成功 → 遮罩淡出，画面续流；**副作用即时恢复**
   （重发一次 `quality` 控制帧同步画质档位）

**哪些情况自动重连**（白名单式，避免无限重试必然失败的场景）：

| 断线原因 | 是否自动重连 |
|---|---|
| 网络超时 / IO 异常 / 隧道断开 | 是 |
| 看门狗触发（30s 无数据 / 无视频帧） | 是 |
| 用户主动点断开 | 否 |
| 验证码错误 / 验证失败 | 否 |
| 服务器明确拒绝、设备不存在 | 否 |

### 改动点

| 文件 | 改动 |
|---|---|
| `SessionViewModel.kt` | 状态机新增 `Reconnecting(attempt, nextRetryAt)`；退避调度、白名单判定、成功后恢复画质 |
| `RemoteSessionScreen.kt` | 重连浮层（保留最后一帧 + 倒计时 + 立即重试/取消） |
| `RemoteSessionManager.kt` | 暴露可重入的 `reconnect()`，避免复用已关闭的会话级资源 |

> **实现警示（来自本项目既有教训）**：会话级资源（帧队列 `BlockingCollection`、
> 输出流、解码器）必须在**每次重连时重建**。历史提交 `b837eb1` 已踩过一次
> ——复用被 `CompleteAdding()` 关闭的队列，导致第二次连接秒断，
> 日志特征是 `session started` 紧接 `Encode loop ended`。

### 验收

- 飞行模式开关一次 → 无需手动操作即自动恢复画面
- 重连过程中画面**保留最后一帧**而非黑屏
- 倒计时归零前点「立即重试」即刻发起
- 连续断网超过 8 次 → 停在上限并显示手动按钮，不无限重试耗电
- 验证码错误导致的断开**不**触发自动重连

## 7. 协议与兼容性

**本轮不新增帧类型，不修改帧头**，全部复用 `TYPE_CONTROL (0x05)` 的 JSON 分发：

| action | 方向 | 引入版本 |
|---|---|---|
| `quality` | Android → PC | 已有（v1.1.20 / v1.0.25） |
| `clipboard` | 双向 | 本轮新增 |

**版本错配行为**：旧版 PC 收到未知 `action` 走现有 `HandleControlFrame` 的
无害忽略路径（仅记日志），不会断连。因此本批功能均为**向后兼容**，
不强制两端同时升级。F2 扫码配对为纯客户端功能，与对端版本无关。

## 8. 测试策略（重要偏差说明）

**现状：本项目当前没有任何测试基础设施。**
- `android-app/app/src/` 下只有 `main`，无 `test` / `androidTest` 源集
- 根目录无 `.sln`，`pc-client` 等三个工程均无对应测试工程

因此 strict TDD（先写失败测试）在本轮**无法立即执行**。
本轮采取如下策略，并建议作为后续技术债优先补齐：

1. **先补最小测试脚手架**（本批次第一步）
   - Android：`src/test` + JUnit，仅跑纯 JVM 逻辑
   - PC：新增 `pc-client.Tests`（xunit）
2. **对可纯函数化的逻辑强制 TDD**（这些是真正容易出错的地方）
   - 配对载荷的 `encode / decode`（base64url、版本校验、字段缺失、损坏输入）
   - 剪贴板分片的 `split / assemble`（边界：正好 64KB、多片、缺片超时、超长拒绝）
   - 重连退避序列与白名单判定（1,2,4,8,15,15… 与 8 次上限）
3. **UI 与网络路径**用人工验收清单（见各 F 的「验收」），
   因为 Compose UI 与真实中继链路不适合在无基建前提下做自动化

**不发版就不算完成**：所有改动需在真机 + 真实中继上走一遍验收清单。
